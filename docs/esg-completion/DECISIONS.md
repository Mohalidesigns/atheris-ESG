| D17 | Authentication & RBAC design choices (WP-12/13) | **DECIDED** — architect (Claude), WP-12/13, 1 Oct 2026; for team review | (1) **Refresh token only in an HttpOnly, Secure, SameSite=Strict cookie** scoped to `/api/v1/auth`, never in the response body, so page scripts can't read it. (2) **Reuse detection with a 30-second grace**: replaying a rotated token within 30 s is just rejected (two tabs refreshing at once); later replays revoke every session. (3) **Permissions and org scopes are reloaded from the database on every request**; JWT role/permission claims are informational. That's what makes expiry and deactivation immediate, at the cost of one extra query per request (cache in WP-51 if needed). (4) **MFA is not enforced in the `local` profile** (developer convenience); every other profile enforces TOTP for SUPER_ADMIN, TENANT_ADMIN and ESG_DIRECTOR. (5) **One generic message** for unknown email, wrong password, disabled and locked accounts (no enumeration); locked users aren't told they're locked. (6) **No privilege escalation** = an assigner may grant a role only if they hold all of its permissions. (7) **Org scope** is the union over a user's active assignments; any unscoped assignment makes the user tenant-wide. (8) **TENANT_ADMIN excludes `whistleblower:*`** (case content is for designated investigators, WP-34) and `tenants:*`. **Known gaps** (scheduled): CONSULTANT multi-tenant access (consultant portal); SUPER_ADMIN still lives inside a tenant until a platform tenant exists (WP-14); self-service forgot/reset password and password change need email (WP-15); admin MFA reset and admin password reset (WP-14); SSO after G2 (D14). *Update WP-14/15:* platform tenant management and admin MFA/password reset are done (WP-14); self-service password reset is still open (needs an email-verified flow). | WP-12/13 |
| D18 | Cross-cutting services design (WP-14/15) | **DECIDED** — architect (Claude), WP-14/15, 1 Oct 2026; for team review | (1) **Audit trail by database trigger, not Kafka + audit-service** (TRD §6.6.1): `audit.log_change()` runs on every tenant table, so no write path (API, import, SQL fix) can skip it, and it's atomic with the change. It records only changed columns on update, redacts secrets, and takes actor, IP and user agent from session settings set per request. Guard triggers make `audit_logs` and `data_lineage` immutable even for the schema owner. Search is SQL with indexes until volume needs Elasticsearch (WP-51). TRD's `change_logs`/`access_logs` are covered by `audit_logs` before/after values and `files.file_access_log` for now. Excluded as noise or secrets: login identities, sessions, role-permission sync, queues and logs themselves. (2) **Notifications are created after the business transaction commits** (separate transaction), so a template or channel problem can't roll back the user's change, and nothing is sent for a change that rolled back. (3) **Email/SMS go through an outbox** (`delivery_log`) drained by a dispatcher (`FOR UPDATE SKIP LOCKED`, 5 attempts, backoff); a channel with no configuration is marked `skipped`, never `sent`. In-app notifications are polled every 60 s instead of WebSocket. (4) **Files: uploads always go through the API** (extension + leading-bytes check, size, SHA-256), only downloads use pre-signed URLs; filesystem storage is allowed in `local`/`test` only. SSE-S3 (AES-256) is on by default and off for MinIO without a KMS. Virus scanning is a hook with no scanner yet: files are marked `not_scanned` and the UI says so. (5) **Reporting-period locks are enforced twice:** in the services (friendly 409) and by a trigger on data tables (`P0L01`), so bulk/SQL paths can't write into a locked period. (6) **Platform tenant operations** run through `SECURITY DEFINER` functions that re-check the caller's `tenants:*` permission in the database. (7) **`auth.organisations.parent_org_id`** now uses a same-tenant composite FK too (V015; it was the one plain tenant-to-tenant FK left, found during WP-14/15 review). | WP-14/15 |

| D21 | Data Hub workflow, quality score, currency and rules (WP-20) | **DECIDED** — architect (Claude), WP-20, 1 Oct 2026; quality sub-scores and rule thresholds **for ESG SME sign-off** | (1) **Workflow states** draft → submitted → validated → approved, rejected back to the submitter (BRD M1 card, F1.3 default); the TRD's 'pending' became 'submitted' and 'flagged' is now a rule warning, not a state. Old rows were migrated in V018. (2) **Segregation of duties**: the creator/submitter can't validate, approve or reject; the approver can't be the validator. New permission `data_points:validate` (analyst, manager, director); `data_points:approve` stays with the director. (3) **Approved data is locked by a database trigger**; reopening needs `data_points:approve` and a reason and returns the point to draft. (4) **Quality sub-scores** (TRD names them, doesn't define them): completeness = expected attributes present (value, evidence, data source; + currency for money metrics); consistency = max(0, 1 − |v − mean| / |mean|) vs the org's validated/approved like-length periods in the previous 24 months (1 with no history); timeliness = 1 up to 30 days after period end, linear to 0 at 365; accuracy = warning checks passed ÷ applicable (1 when none). Score rounded half-up to 2 dp. Golden tests in QualityScoreCalculatorTest. (5) **Rules engine**: range and cross-metric rules are data (`reference.metric_rules`, R__ref_06); 'error' blocks saving and is mirrored in the form, 'warning' is stored with the point and lowers accuracy. Duplicates (same org, metric, period) are errors; overlapping periods and periods not yet ended are warnings. The plausibility thresholds are Atheris defaults, not published values. Warnings are computed when a point is saved or submitted; a later change to the other metric doesn't refresh them. (6) **Currency**: money metrics store the base-currency value plus original amount, currency, rate, rate date and source; the rate is the tenant's latest dated on or before the period end; no rate → field error. No FX rates are seeded or fetched until an FX provider adapter exists (rule 9). (7) **API paths follow the TRD catalogue**: workflow steps are `PUT /api/v1/data/points/{id}/{submit|validate|approve|reject|reopen}` (TRD lists PUT …/validate); import is under `/api/v1/data/import` (TRD POST /api/v1/data/import), as upload → map → start. (8) **Bulk import**: up to 5,000 rows per file, CSV (OpenCSV) or the first sheet of XLSX (Apache POI); each row goes through the same save path as the form, as the importing user on a bounded background executor; rows become drafts. | WP-20 |
